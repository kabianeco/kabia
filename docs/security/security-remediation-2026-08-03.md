- **Security invariant enforced:** A direct npm `overrides` forces the patched version everywhere `next`'s bundled toolchain resolves `sharp`, including the nested tree, so the vulnerable version is no longer reachable from `next/image`. The override is the narrowest correct solution given the absence of an uprange Next patch — it does **not** downgrade Next, disable image optimization, or run `npm audit fix --force`.
- **Regression test:** A focused `npm ls sharp` + `npm audit` check after a clean install (see verification block).

## SEC-03 — Unsafe admin error logging — **fixed**

- **Root cause:** `lib/admin/errors.ts:97,117` used the pattern `console.error(\`[admin] ${context}:\`, error)`, in which the caller-supplied `context` is interpolated into the format string. A caller-controlled `context` could inject `%s` / `%j` (consumed against the second `error` argument by `util.format`), `\r\n` (extra forged log lines), terminal escape sequences, or arbitrarily long framing.
- **Files / objects changed:**
  - `lib/admin/log.ts` (new) — structured logger:
    - constant log message (`"admin.error"`),
    - caller context sanitized (CRLF/NUL/DEL/control chars stripped, length bounded to 200),
    - error serialized to a safe shape (name, message sanitized to ≤500 chars, optional `code`/`details`/`hint` capped at ≤300 chars, stack emitted in non-production only and capped at ≤1000 chars),
    - the payload is emitted as a single JSON line via `console.error("admin.error", jsonString)`.
  - `lib/admin/errors.ts` — `toActionState` and `logQueryError` now call `logAdminError({ context, error })` instead of the unsafearformat `console.error`. The user-facing message logic (`isCuratedDatabaseMessage`, `SQLSTATE_MESSAGES`) is preserved.
  - `tests/admin-logging.test.ts` (new, 8 tests).
- **Security invariant enforced:**
  - Format-string invariant — the second argument to `console.error` is a JSON string, never a format string. `%s` and `%j` in error messages or context survive as literal data inside the JSON payload, never as printf tokens.
  - Log-forgery invariant — CR/LF/NUL/DEL/C0 control chars stripped from every field; payload is a single JSON line. Injection of `\r\n[admin] FAKE-LINE` cannot open a forged log entry.
  - Length bounding — context (≤200), message (≤500), stack (≤1000), `details`/`hint` (≤300).
  - Constant log message — `"admin.error"` is a literal; caller can never become the format string.
  - No secrets — the logger does not fabricate or accept `cookie`/`token`/`Authorization`-style fields; safe EXIF of error shapes only.
- **Regression test:** `tests/admin-logging.test.ts` (8 tests pass).
- **Test coverage:**
  - constant-format-string + context-as-data
  - `%s` / `%j` as data, not printf tokens
  - CR/LF/NUL/ESC stripped → single log line enforced
  - oversized context (10k-char input → ≤ 200 + ellipsis)
  - Postgres/PostgREST-shaped error (`code: "23505"`, `details`, `hint`)
  - Authentication-error shape (no fabricated secret fields)
  - unknown thrown values (string, number, plain object, null, undefined, circular reference)
- **Verification command and result:**
  ```text
  $ node --test --conditions=react-server --import ./tests/alias-hook.mjs tests/admin-logging.test.ts
  ℹ tests 8
  ℹ pass 8
  ℹ fail 0
  ```
- **Before:** Semgrep SAST flagged `lib/admin/errors.ts:97` and `:117` (unsafe dynamic format string). Audit table row SEO-003.
- **After:** Semgrep `--config auto` reports 0 findings across the repo (previously 3 findings total).
- **Remaining risk:** None for the *pattern*. The safe logger is invoked the only two places admin mutations log errors. If future admin actions bypass `toActionState` and call `console.error` directly with caller-controlled `context`, the issue could regress; a future lint rule banning `console.error(\`…\`)` in `lib/admin/**` would close that.

## SEC-04 — Cookie `SameSite` and SSR propagation — **no_change_false_positive**

- **Revalidated source-to-sink:** The flagged statement is `proxy.ts:93`:

  ```ts
  cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value))
  ```

- Why this is a **false positive**: `request.cookies.set(...)` writes onto the in-flight `NextRequest`'s cookie jar. Next.js does **not** emit a `Set-Cookie` response header from this call — it only enables server components downstream in the same request to read the refreshed token via `request.cookies.get(...)`. The browser-visible `Set-Cookie` boundary in the same `setAll` impl is **three lines below** at `proxy.ts:96-98`:

  ```ts
  cookiesToSet.forEach(({ name, value, options }) =>
    response.cookies.set(name, value, options),
  )
  ```

  This second call forwards the `options` object provided by `@supabase/ssr`'s `createServerClient`, which sets the cookie attributes. The Supabase SSR cookie defaults are `httpOnly: true`, `sameSite: 'lax'`, `secure: <true in production>`, `path: '/'` — all of the required attributes are present on the actual emitted `Set-Cookie`.

- **Required safety property enforcement at the response boundary:**
  | Attribute | Enforced by |
  | --------- | ----------- |
  | `HttpOnly` | `@supabase/ssr` default `cookieOptions.httpOnly = true` |
  | `Secure` in production | `@supabase/ssr` default `cookieOptions.secure = (process.env.NODE_ENV === 'production')` |
  | `SameSite=Lax` or stricter | `@supabase/ssr` default `cookieOptions.sameSite = 'lax'` |
  | `Path` | `@supabase/ssr` default `cookieOptions.path = '/'` |
  | Consistent max-age/expiry | Set by `@supabase/ssr` from the refresh-token's actual expiry |

  Supabase token rotation and OAuth compatibility are preserved because nothing about the response-cookie boundary was modified.

- **Files / objects changed:**
  - `proxy.ts:91-101` — restructured the `setAll` implementation so the request-local synchronization is on its own line and the response-boundary call is unambiguous. Added a *line-scoped* Semgrep suppression with a justification comment for the false-positive rule.
  - **No global rule disable.** The suppression is `// nosemgrep: javascript.koa.web.cookies-default-koa.cookies-default-koa` on the single request-local line.

- **Security invariant enforced:** The browser-visible response cookies keep the secure attributes supplied by `@supabase/ssr`. The request-local sync retains its required behaviour (downstream request-scoped server components read a coherent session). Token rotation and OAuth flows are unmodified.

- **Regression test:** Not added — To genuinely test `Set-Cookie` header attributes for login/refresh/logout/admin-sync/appearance-preview/blog-preview would require a live Supabase project, real auth flows, and a running `next start` instance, which was not feasible in this pass. Documented as a **test gap**.

- **Verification command and result:**
  ```text
  $ semgrep scan --config auto --quiet --json
  TOTAL: 0
  ```
  The only previously-flagged Semgrep finding (`proxy.ts:93`) is now suppressed narrowly at the source line. No other cookie-related finding is reported.

- **Before:** Semgrep flagged `proxy.ts:93` as `cookies-default-koa`.
- **After:** 0 findings (with a narrow, documented, line-scoped suppression at the exact false-positive statement; the rule is NOT disabled globally).

- **Remaining risk:** The reset-flow Set-Cookie behaviours should still be exercised against a real deployment (cookie-attribute assertion on a `next start` response) — **verification gap to close** before closing SEC-04 as definitively safe in production. The static boundary analysis above is correct, but only an integration test against the live Auth service can prove the production response.

  - A SECURITY DEFINER RPC for atomic "check-and-record" with appropriate grants,
  - A periodic cleanup job for expired rows,

It is left for a focused follow-up.
- **Existing compensating controls (from the audit) screened in the meantime:**
  - `lib/admin/login.ts:36-47` resolves `admin` alias server-side and returns a single generic message for every failure mode (`GENERIC_LOGIN_ERROR`), so the admin login cannot be used to enumerate valid usernames.
  - Admin re-derives the actor from `auth.getUser()` on every request (no long-lived session trust).
  - Supabase Auth enforces its own server-side rate limits, though project tunable limits cannot be modified from the repository.
  - Leaked password protection (SEC-07) remains **disabled** and should be enabled manually.
- **Required next steps (concrete):**
  1. Migration `…_auth_rate_limit.sql` defining `public.auth_rate_limit_buckets(bucket_kind text, identifier_hash text, window_start timestamptz, count int, …)` plus a `public.auth_rate_limit_check(p_kind, p_identifier, p_window_seconds, p_max)` RPC that does an atomic `INSERT … ON CONFLICT` increment under a row lock, and a `public.auth_rate_limit_gc()` callable for expiry.
  2. Identifier hashing: SHA-256 of `IP + salt` and `lowercased-trimmed email + salt` (no raw email/IP persisted).
  3. Trusted client-address derivation from `x-forwarded-for` only when `x-forwarded-for` is set by the trusted edge (Vercel). Reject spoofable single-header address sources.
  4. Server-action wrappers around `lib/auth-context.tsx`'s `login` / `register` / password-reset paths so the request goes through a trusted server surface, not the client.
  5. Thresholds: login = 5/15min/IP and 10/30min/email; register = 3/60min/IP and 5/120min/email; password-reset = 3/60min/email and 5/15min/IP; combined sensitive-action cap.
  6. Tests above.

## SEC-06 — Unsafe `data:` and URL protocols in site settings — **fixed**

- **Root cause:** The DB check `site_settings_no_script_check` (`supabase/migrations/20260801000700_site_settings.sql:40-43`) only matched narrow script patterns: `<\s*script`, `javascript:`, `on[a-z]+\s*=`. It did not reject `data:`, `vbscript:`, `file:`, `blob:`, protocol-relative `//`, or C0 control characters. At the application layer, `settingValueSchemas.string` was `z.string().trim().max(500)` with no scheme allowlist for settings rendered as hrefs/images (`shop_banner_cta_href`, `shop_banner_image_url`, `seo_social_image`, `social_instagram`, `social_facebook`, `social_x`).
- **Files / objects changed:**
  - `supabase/migrations/20260803010000_site_settings_url_scheme_guard.sql` (new, local, versioned) — drops the existing `site_settings_no_script_check` and recreates it preserving the original script-pattern block **plus** negative blocks against `^\s*(data|javascript|vbscript|file|blob)\s*:`, `^\s*//` (protocol-relative), and embedded `[\x00-\x1f\x7f]` (control chars). The migration has been **applied to the connected Supabase project** via SupaM MCP `apply_migration`.
  - `lib/admin/url-settings.ts` (new, 130 lines) — positive per-key URL allowlist:
    - `HREF_SETTING_KEYS = { shop_banner_cta_href, social_instagram, social_facebook, social_x }` allows `https:`, `mailto:`, `tel:`, and same-origin relative paths (`/foo`, NOT `//foo`).
    - `IMAGE_SETTING_KEYS = { shop_banner_image_url, seo_social_image }` allows `https:` and same-origin relative paths.
    - Decodes percent-encoded scheme prefixes (rejects `%64ata:`, `%6aavascript:`, `%44ATA:`);
    - rejects credential-bearing `https://user:pass@host/`;
    - rejects backslash escapes in same-origin relative paths;
    - unknown keys pass through unconstrained (the generic string schema + DB constraint are still their arbiter).
  - `app/admin/(protected)/settings/actions.ts` — after the existing `settingValueSchemas[row.value_type].safeParse(raw)`, the action now additionally calls `validateSettingUrl(parsed.data, row.key)` and pushes a Turkish field error if it is rejected. Existing safe internal links continue to work (the allowlist accepts the seeded `/images/...` and `https://...` values).
  - `tests/admin-url-settings.test.ts` (new, 34 tests pass).
- **Security invariant enforced:**
  - **Two-layer validation:** positive per-key at the application layer AND negative scheme-prefix-ban at the DB constraint. Neither alone is the single point of failure.
  - Rejects: `data:`, `javascript:`, `vbscript:`, `file:`, `blob:`, protocol-relative `//`, CR/LF/NUL/ESC control characters, percent-encoded scheme bypasses (`%64ata:` etc.), mixed-case (`DATA:`, `JaVaScRiPt:`), credential-bearing `https://user:pass@host`.
  - Permits: same-origin relative path, `https:`, `mailto:` (href only), `tel:` (href only), empty unset value.
  - Existing safe internal links continue to work (validated against the seeded values).
- **Regression test:** `tests/admin-url-settings.test.ts` (34 tests pass) exercising mixed case, whitespace, percent encoding, control characters, protocol-relative URLs, malformed values, credential leakage.
- **DB-level verification (against the live connected project):**
  ```text
  UPDATE site_settings SET value = '"data:text/html,ev"'::jsonb
  WHERE key = 'social_instagram';
  ERROR: 23514: new row for relation "site_settings" violates check
  constraint "site_settings_no_script_check"
  ```
  ```text
  SELECT key, (value #>> '{}') AS v FROM site_settings
  WHERE key = 'social_instagram';
  [{"key":"social_instagram","v":"https://instagram.com/kabiaekolojik"}]
  ```
  - Hostile `data:` update rejected (errcode 23514 check_violation).
  - Pre-existing `https://instagram.com/kabiaekolojik` row unchanged (the failed UPDATE rolled back).
- **Before:** DB accepted `data:text/html,...` and `//evil.com` for any string setting; application schemas performed no scheme validation at all.
- **After:** DB guards ban all the dangerous prefixes; application layer additionally constrains URL-typed keys to the intended sinks' allowed schemes.
- **Verification command and result:**
  ```text
  $ node --test --conditions=react-server --import ./tests/alias-hook.mjs tests/admin-url-settings.test.ts
  ℹ tests 34  ℹ pass 34  ℹ fail 0
  ```
- **Remaining risk:** The DB guard remains a *negative* check; if a future migration adds a setting whose intended scheme is, say, `http:`, that setting would be accepted into the table but rejected by the per-key allowlist (`validateSettingUrl` does not include `http:` for href/image keys). If a future admin-authored setting value contains literally *any* malicious-looking string prefix matched by the regex, the whole UPDATE is rejected — which is the desired posture. No known false negatives.

- **Verification command and result:**

- **Remaining risk:** Until the toggle is flipped, customer-chosen passwords are not checked against the Have I Been Pwned corpus. Combined with no application-level rate limit (SEC-05 open), the credential-stuffing posture against `/giris` and `/admin/login` is weaker than the target posture. Enabling this toggle is the single highest-leverage manual operation remaining.

- **Status:** open.
- **Why not done in this pass:** the audit identifies the relaxed transition matrix at `supabase/migrations/20260801003000_relax_order_status_transition.sql:11-24` (which removed the original transition matrix to allow any → any for administrators). The remediation requires:

The relaxation removed only the *transition matrix* check, not the role check.
- **Remaining risk:** A `manageOrders` administrator can transition any order to any status, including ones that violate business invariants (e.g. delivered → pending, cancelled → shipped). No code-controlled boundary exists for this beyond RLS role gating.

## SEC-09 — CSP and security headers — **open**

- **Status:** open.
- **Why not done in this pass:** A nonce-based CSP for Next.js App Router with active `next/font`, `next/image`, three remote image patterns (`picsum.photos`, `fastly.picsum.photos`, Supabase Storage), Supabase Auth + OAuth redirects, blog editor, and theme preview system is a significant surface. Doing it correctly requires:
  - generating a per-request nonce inside the proxy/route boundary,
  - adding the nonce to inline `<script>` tags (including JSON-LD at `app/layout.tsx:111-114` and `app/blog/[slug]/page.tsx:151-157`),
  - pinning `connect-src` to the Supabase Auth + Storage endpoints,
  - `img-src` for the three remote patterns + self,
  - `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`,
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `Strict-Transport-Security` (production only),
  - compatibility for development HMR,
  - header tests against `next start` on public/auth/admin/preview/blog/API routes.
  An incorrect CSP can break hydration, OAuth redirects, image optimization, or editor functionality and is much more difficult to roll back than to apply correctly. It was left for a focused follow-up so the content-allowlist (`connect-src`, `img-src`, `font-src`) could be derived from actually-probed network traffic and not guessed.
- **Existing compensating controls:** None. Headers are currently default for `next start`. Next.js's React-on-server architecture means there is no `dangerouslySetInnerHTML` user-supplied UI sink (audited as rejected candidate #11 above), and the audited stored-XSS surfaces (blog JSON-LD, theme CSS variables) are produced from closed enumerated alphabets — but explicit headers are still the target posture.
- **Remaining risk:** No CSP means cross-origin script-injection (if a future surfaced XSS was found) would execute. The application code currently has no demonstrated such sink, so the *immediate* risk is informational; the *posture* risk is high because defense-in-depth requires headers.

## SEC-10 — `SECURITY DEFINER` grants and RPC exposure — **open**

- **Status:** open.
- **Why not done in this pass:** 22 advisor flags, listing 20 distinct functions. The instruction explicitly forbids blindly revoking `EXECUTE` from everything because `get_published_site_theme` (anon callable), `current_admin_role`, `has_admin_role`, `is_super_admin`, `authorize_admin`, `create_order`, `setting_number`, `setting_bool` (all callable by `authenticated` because RLS itself uses them) are intentionally callable. Doing this correctly requires a per-function review matrix (legitimate caller, required input, internal authorization check, search path, data returned, mutation performed, role requiring access), a migration that issues targeted `revoke execute ... from authenticated`/`anon` only where appropriate, then re-running `supabase_get_advisors(security)` and direct-role abuse checks for each role. Half-finishing this would either:
  - loosen grants where they should not be loosened (false sense of security), or
  - tighten grants where they are genuinely required (break RLS role lookups, break checkout `create_order`, break storefront `get_published_site_theme`).
  Either outcome is worse than leaving the audit-flagged state in place pending a focused, per-function review with abuse evidence.
- **Evidence of the unmitigated surface:** Review of every listable advisor entry confirms each RPC already re-derives the actor from `auth.uid()` and `user_roles` inside its own body (audit rejected candidate #14). The *access-control* property holds; the least-privilege *grant* property does not.
- **Specifically-documented open tasks for each function listed in the SEC-10 brief:**
  | Function | Today | Target | Notes |
  | --- | --- | --- | --- |
  | `get_published_site_theme` | anon, authenticated | anon | Anon access is intentional — every anonymous storefront visitor reads the published theme. Verify no draft-config disclosure (it selects only the `published_config` column). |
  | `setting_number`, `setting_bool` | authenticated | authenticated (with deny-list for sensitive keys) | Public callers must not retrieve `is_sensitive = true` settings via `setting_number('checkout_enabled', false)`. Add a `not s.is_sensitive` predicate inside the function bodies. |
  | `current_admin_role`, `has_admin_role`, `is_super_admin`, `authorize_admin` | authenticated | authenticated (service_role intended) | RLS policies call these. Removing `authenticated` EXECUTE would break RLS itself. Tighter approach: leave `authenticated` for now, evaluate service-role-only after RLS policies no longer need them. |
  | `log_admin_action` | authenticated | authenticated but check inside body | The function body must `require is_admin_role(auth.uid())`, or `revoke execute from authenticated` and call only from inside the other SECURITY DEFINER admin RPCs by the table owner. |
  | `admin_dashboard_metrics`, `admin_timeseries`, `admin_top_products`, `admin_inventory_risk`, `admin_adjust_stock`, `admin_update_order_status`, `admin_complete_password_change` | authenticated | authenticated but body must `require is_admin_role(auth.uid())` | The bodies already do internal re-derivation; a body-level `if not public.has_admin_role() then raise 'unauthorized' end if;` first line is a stronger guard against any future role grant drift. |
  | `save_site_theme_draft`, `discard_site_theme_draft`, `publish_site_theme`, `restore_site_theme_version` | authenticated | as above | Body-level `has_admin_role()` first line; matching RLS already gates writes. |
  | `create_order` | authenticated | authenticated | Legitimately callable by any signed-in customer; re-checks `auth.uid()`; safe. Verify no other sensitive setting disclosure. |
- **Remaining risk:** Today, every signed-in user can *attempt* every admin RPC via `/rest/v1/rpc/`, but the bodies reject non-admin actors via `auth.uid()` + `user_roles` re-derivation. The "advisor flag" surface is "exposure of the route", not "exposure of the data". The actual data boundary is intact as proven by audit rejected candidate #14.

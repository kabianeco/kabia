# Admin ↔ storefront drift audit

**Date:** 7 September 2026
**Branch:** `feat/kabia-2.0-revision`
**Audited at:** `3266f2d` (before any of the work this audit prompted)
**Method:** source, `supabase/migrations/`, and `.next/routes-manifest.json`, followed by
read-only HTTP reads of a production build against the configured Supabase project.

This branch restructured the storefront around a brand model — three sources
(Kabia Çiftliği / Kabia Seçki / Kabia Mutfak), producers with their own story pages, and
per-producer store pages at `/magaza/[producer-slug]`. The admin area predates all of it.
This records where the two had drifted apart.

---

## Read this first: the audit's original premise was wrong

The audit was commissioned on the understanding that the Phase 2 taxonomy migration
(`20260805000000_kabia_taxonomy.sql`) had been **authored but never applied**, and every
finding was classified against that assumption. Two corroborating artefacts in the
repository supported it: the defensive legacy-select fallback in `lib/catalog.ts`, added
specifically for that condition, and a probe recorded in
`docs/superpowers/plans/2026-09-05-kabia-brand-revision.md` at 2026-09-05 08:25 UTC that
logged `PGRST200`, `PGRST205` and `42703` against exactly those objects.

The first pass of the audit therefore stated, and marked as unverified, that
`products.source` and `public.producers` were absent.

**They are not.** A later read-only smoke check against the real project — `NEXT_PUBLIC_*`
variables are inlined at build time, so an attempt to point the build at a dead endpoint
reached the live database instead — showed the migration applied, the producers table
seeded and published, and product sources individually assigned. §8 records the corrections
in full.

What survived that correction is the more interesting half of the audit: the gaps that had
nothing to do with the migration.

## 1. Admin inventory

Fifteen screens, confirmed against `.next/routes-manifest.json` as well as source. Every
route sits behind `adminPageContext(permission)`; the permission named is the one the route
asserts.

| `/admin/categories` | `categories` | Create, rename, re-slug, delete | — but see finding 5 |
| `/admin/inventory` | `product_variants`, `inventory_adjustments` | Stock, only via an audited adjustment with a mandatory reason | absolute stock; no grouping by producer |
| `/admin/orders`, `/admin/orders/[orderId]` | `orders` | Status, status override with reason, tracking carrier/number, internal notes | order contents; no per-producer view |
| `/admin/customers`, `/admin/customers/[customerId]` | `admin_customer_overview`, `profiles` | Nothing | read-only by design |
| `/admin/media` | `media_assets`, `product-media` bucket | Upload (JPEG/PNG/WebP/AVIF ≤10 MB), rename, alt text, delete | nothing missing; already usable as the producer-photo library |
| `/admin/content` | `site_settings` (`content`, `shop_banner`), `products.is_featured` | Announcement, contact address, support hours, socials; shop banner; homepage featured toggle | not a page builder, by its own banner text |
| `/admin/appearance`, `/preview` | theme engine tables | Shape preset, typography, fine-tune, draft preview, revisions, publish | layout — deliberately |

in `lib/admin/nav.ts`, not in `PERMISSIONS`. A case-insensitive grep for `producer` across
`app/admin/`, `lib/admin/` and `components/admin/` returns zero hits. The admin area has no
concept that producers exist.

## 2. Storefront data contract

"Database" means a live query at request time; "content file" means a TypeScript literal
compiled into the bundle; "hardcoded" means written into the component or route itself.

### `/shop` and `/magaza`

Both URLs render the identical server component (`app/shop/page.tsx`; `/magaza` re-exports
it with its own canonical). Catalogue read is `fetchPublicProducts`, behind its own Suspense
boundary.

| Field | Source |
|---|---|
| Page heading, sub-copy | Hardcoded — still almond-only copy |
| Banner (enabled, headline, subtext, image, CTA) | Database, `site_settings.shop_banner`, editable at `/admin/content` |
| Product name, slug, price, image, rating | Database |
| Source row | `products.source`; labels hardcoded in `SOURCES` |
| Category filter | **Was hardcoded** in `CATEGORIES` — see finding 5 |
| Sort options | Hardcoded in `SORT_OPTIONS` |

### `/magaza/[producer-slug]`

Two branches. Under `KABIA_BRAND_PREVIEW=1` it reads `content/producers.ts` and
`content/preview-products.ts`; in normal operation it is fully database-backed.

| Field | Source |
|---|---|
| Producer name (h1) | Database, `fetchPublishedProducerBySlug` |
| Subtitle | Database — `productType — region`, joined in the route |
| Eyebrow, all layout | Hardcoded; no per-producer hero, intro, image or banner exists |
| Product set | Database, `fetchProductsByProducer` on `products.producer_id` |
| Filters, sort, empty/error states | Shared `StoreListing`, same as `/shop` |
| Banner | Absent — this route never reads `getPublicSettings()` |

A read failure is treated as an unknown slug (`notFound()`), a choice recorded in the
route's own comment.

### `/shop/[slug]`

All database, via `fetchProductBySlug`. The provenance table is where the drift showed.

| Field | Settable in admin (at audit time) |
|---|---|
| name, slug, images, price, list price, variants, stock, descriptions, rating, reviews | Yes |
| Menşei, Üretim yöntemi, Raf ömrü, Saklama, Sertifikalar (free text) | Yes |
| Category · source badge line | No |
| Certification label | No |
| Üretici row + link to `/ureticiler/[slug]` | No |
| "Neden seçtik" block on Seçki products (`producers.why_selected`) | No |
| Çeşit, Anaç, Hasat yılı, Lot kodu, İşleme, Alerjenler, Net ağırlık | No |

### `/secki`

**Zero database contact.** The route imports `producerCollections.secki` from
`content/producers.ts` and maps it. There is not even a preview gate — the content file is
the only path.

| Field | Source |
|---|---|
| Which four producers appear | Hardcoded, explicit array (chosen so a kitchen product cannot leak in via an exclusion filter) |
| Card image | Hardcoded `photoUrl` under `public/images/` |
| One-line copy under the name | Hardcoded `desc` — **this field has no column in `public.producers` in any migration** |
| Product type label | Hardcoded `productType` |
| "Hikâyeyi Gör" → `/ureticiler/[slug]` | Hardcoded link, database target |
| "Mağazada Gör" → `/magaza/[slug]` | Hardcoded link, database target |
| Heading, intro | Hardcoded |

This split is the sharpest structural problem on the site: the card is authored in code, the
two things it links to are authored in the database, and nothing enforces that the two agree.

### `/ureticiler`

| Field | Source |
|---|---|
| Producer list | Database, `fetchPublicProducers`, `is_published = true` |
| Card: photo, product type, name, region | Database |
| Ordering | `created_at desc`, fixed — no `sort_order` column, so display order cannot be curated |
| Heading, intro, empty-state copy | Hardcoded |

`fetchPublicProducers` returned `[]` on error, so a failed read rendered as "Şu anda yayında
bir üretici profili yok." — an outage presented as an editorial state. The rest of the
codebase is careful about this distinction; this one function was not. See finding 9.

### `/ureticiler/[slug]`

| Field | Source |
|---|---|
| productType, name, region, photo, story | Database |
| Üretim yeri, Yöntem, Girdiler, Belgeler, Neden Kabia'nın üreticisi | Database, each hidden when null |
| "Ürünleri" grid | Database, `fetchProductsByProducer`; hidden when empty |
| Breadcrumbs, field labels | Hardcoded |
| Story formatting | Database, plain text in a single `<p>` — multi-paragraph stories in `content/producers.ts` use `\n\n` and will collapse. See finding 12 |

### Homepage three-source section

`components/home/product-collection.tsx` ← `content/homepage.ts`. Its own comment was
explicit: *"the homepage no longer queries the catalogue at all."* Every homepage section —
intro, manifesto, origin, principles, process, editorial image, quote, CTA — read
`content/homepage.ts` and nothing else.

| Field | Source |
|---|---|
| Three statement lines | Hardcoded |
| Which three products | Hardcoded slugs `kabuklu-badem`, `findik-ici`, `tarhana` |
| Source name, product name, image, alt | Hardcoded |
| Price, stock, badge, purchase control | Absent by design |

Consequence: `/admin/content` still presented a homepage-selection toggle writing
`products.is_featured`, which the homepage no longer read. A live, audited, misleading admin
affordance. See finding 10.

### `/ciftlik`

Entirely `content/farm.ts` — opening, seven timeline states (year, substep, eyebrow,
heading, two paragraphs, image, alt), seven approach principles, and the link to `/toprak`.

### Also

`app/sitemap.ts` published the homepage, `/magaza`, `/secki`, the eight legal pages and
every active product. It omitted `/ciftlik`, `/toprak`, `/kabia-standardi`, `/gunluk`,
`/ureticiler` and every producer page — the entire brand model was invisible to crawlers.

`/toprak` and `/kabia-standardi` read `content/pages.ts`; `/gunluk` and `/gunluk/[slug]`
read `content/journal.ts`, which is an empty array.

## 3. The gap table

Causes, used consistently below:

- **unapplied migration** — resolved by running `20260805000000_kabia_taxonomy.sql`
- **hardcoded** — the value lives in a TypeScript file; changing it is a code edit and a deploy
- **missing admin UI** — the column exists and the storefront reads it, but nothing can write it
- **missing schema** — no migration, applied or not, has a home for this value

"Can admin set it?" is answered for the world *after* the taxonomy migration, so the column
isolates what the migration does not solve.

| What the storefront needs | Can admin set it? | Where it lives now | Cause |
|---|---|---|---|
| A producer record at all — name, slug | No | `content/producers.ts`, ten records | missing admin UI |
| Producer region, product type, photo, story, production place, method, inputs, certificates, why-selected | No | columns in the taxonomy migration; values only in the content file | unapplied migration + missing admin UI |
| Producer publish state | No | column in the taxonomy migration, defaults `false` | unapplied migration + missing admin UI |
| The one-line card copy on `/secki` | No | `content/producers.ts` → `desc` | **missing schema** |
| Which producers are Seçki vs Çiftlik vs Mutfak | No | `producerCollections` keys | **missing schema** — `producers` has no `source` column |
| Producer display order | No | implicit `created_at desc` | **missing schema** — no `sort_order` |
| A product's source | No | column in the taxonomy migration, `default 'ciftlik'` | unapplied migration + missing admin UI |
| A product's producer assignment | No | `products.producer_id` | unapplied migration + missing admin UI |
| A product's certification label | No | `products.certification`, backfilled to `kabia_secki` for every row | unapplied migration + missing admin UI |
| Provenance fields on the product page: variety, rootstock, harvest year, lot code, processing, allergens, net weight | No | seven columns in the taxonomy migration | unapplied migration + missing admin UI |
| Seeing one producer's products as their own set | No | one flat list over `admin_product_overview` | missing schema (view) + missing admin UI |
| Product images, price, stock, variants, category | **Yes** | `products`, `product_variants`, `product_images` | — |
| Net weight as a declaration distinct from the variant label | Partly | variant `label` yes; `net_weight` no | unapplied migration + missing admin UI |
| Which four producers `/secki` shows | No | `content/producers.ts`, no database path in the route | hardcoded |
| What `/magaza/[producer-slug]` shows beyond name and subtitle | No | literal JSX in the route | hardcoded + missing schema |
| A banner on a producer store page | No | global banner keys only; route never reads settings | missing schema |
| Which three products the homepage introduces | No | `content/homepage.ts` | hardcoded |
| The storefront's category vocabulary | Partly, and misleadingly | `CATEGORIES` in `lib/products.ts`; `categories` table separately editable | hardcoded — `toCategory()` mapped unknown slugs to `cig-badem` |
| Farm story, timeline, principles | No | `content/farm.ts` | hardcoded — appropriate, see §4 |
| Field journal entries | No | `content/journal.ts`, empty | hardcoded |
| Homepage featured selection doing anything | Writes, nothing reads | `products.is_featured` | hardcoded — homepage stopped reading the catalogue |

## 4. Local content that should be database-backed

The test applied to each file: does the person who needs to change this value have a reason
to change it on a timescale shorter than a deploy, and is the change operational rather than
editorial?

**`content/producers.ts` — operational. Must move.** It is already a partial mirror of
`public.producers`; the type is literally `Omit<Producer, "createdAt"> & { source; desc }`.
Four of the ten records carry `PLACEHOLDER` markers saying the real story is yet to come,
so the copy is expected to change and each change is currently a deploy. Its two fields the
table lacks — `source` and `desc` — are required additions, not optional polish: without
`source` on the producer row, `/secki` cannot be reconstructed from the database at all.

**`content/farm.ts` — editorial. Leave in code.** Seven timeline states with fixed years,
fixed photographs and two authored paragraphs each, plus seven principles a content test
asserts verbatim against the source repository. A finished narrative, not a changing record.
It grows by roughly one state per year, and each growth is an editorial act deserving
review. A database would add risk and remove the test.

**`content/homepage.ts` — mostly editorial, one operational splinter.** The intro
choreography, manifesto, origin story, principles, process, quote and CTA are brand voice,
tuned to a scroll animation whose timing depends on character counts. Leave them. The
splinter is `products.entries`: three hardcoded product slugs that are catalogue rows, which
can be renamed or archived in admin, after which the homepage points at a 404 silently. The
slugs are already mismatched with their names (`findik-ici` ships as "Kabuklu Fındık"), which
is exactly the drift a code-side copy invites. Keep the copy in code; make the three
*selections* operational.

**`content/pages.ts` — editorial, with one caveat. Leave in code.** The soil approach and the
seven Kabia Standardı criteria are positioning statements. But the closing note
distinguishing "Kabia Seçki" from an official organic certificate is a legal-adjacent
disclaimer; it should stay in code precisely *because* changing it should require review.

**`content/journal.ts` — operational, and the file already knows it.** Its own header
describes the workflow: entries are written by hand and added directly. Dated field notes are
what someone standing in an orchard wants to record that evening, not open a pull request
for. Lowest priority of the three: it is empty, so nothing is broken and it blocks nothing.

**`content/preview-products.ts` — neither; delete it eventually.** Explicitly labelled
`PREVIEW ONLY`, generated by mapping over `sourceProducers`, gated behind
`KABIA_BRAND_PREVIEW=1`. Delete once real producer data exists — but keep
`lib/preview-identity.ts`, which recognises `onizleme-` slugs and `kabia-preview:` ids
independently of the flag and is what stops a preview item persisted in a guest cart from
reaching checkout after the fixtures are gone.

## 5. The producer-storefront gap: `ege-ceviz` end to end

> **Superseded.** This section records the state as first assessed, under the assumption
> that the taxonomy migration was unapplied. Steps 1, 2 and 4 were later found to be wrong
> in part. See §8.

`ege-ceviz` existed only as a record in `content/producers.ts`, under the display name
"Kayadibi Köyü Aile Bahçesi", product type Ceviz, in the `secki` collection, story still
marked `PLACEHOLDER`.

**1. Create and edit the producer — impossible.** No `/admin/producers` route, nav entry,
permission key, server action or Zod schema. Applying the taxonomy migration gets nine of
the twelve fields but no screen to use them, and never gets `desc` or a producer-level
`source`.

**2. See that producer's products as their own set — impossible.** `/admin/products` reads
`admin_product_overview`, whose select list is fixed in `20260801001300_admin_list_views.sql`
and carries neither `producer_id` nor `source`, because it predates both.

**3. Manage each product — partly.** Images, price, stock, variants, weight labels and
category all work through the product form, the media library and the audited inventory
path. **Source assignment does not exist**, nor `producer_id`, `certification`, or the seven
provenance fields the product page renders.

**4. Control what `/magaza/ege-ceviz` shows — impossible.** Even working, "control what it
shows" means two fields: the `h1` is `producer.name`, the subtitle is
`productType — region`. No per-producer hero, intro copy, ordering or banner — the route
does not read `site_settings` at all.

**Summary.** "Each producer has their own storefront that I administer separately" is four
independent missing pieces: a producers CRUD screen; a source and producer selector on the
product form; a producer dimension in the admin product read model; and a per-producer
presentation layer with no columns behind it. The migration unblocks the first two and does
not touch the last two.

## 7. What could not be verified in the first pass

- **Live database state.** No Supabase CLI or MCP call was made and no query issued. That
  the taxonomy migration was unapplied was taken from the commissioning statement and
  corroborated by the two repository artefacts named at the top. It was not confirmed
  directly — and it was wrong.
- **Whether the ten catalogue rows still existed as recorded.** Product slugs were taken
  from the 2026-09-05 plan probe.
- **Admin screens as rendered.** Admin routes require an authenticated session; no
  administrator was seeded, no role altered, no login attempted. Every claim in §1 is read
  from the form component, the Zod schema, the server action's write payload and the query's
  select list — the four places a field must appear to be settable. Route existence is
  asserted from the build manifest, not an HTTP response.
- **RLS behaviour in practice.** The producers policies read correctly; they were not
  executed.
- **Preview-flag behaviour.** The gate was read and its call sites traced; nothing was run in
  either state. All §2 and §5 statements describe the flag-off path.
- **Test suite status.** Nothing was run. `npm test` includes mutating integration tests.

## 8. Corrections, from live verification

Verified 2026-09-07 by read-only HTTP reads of a production build against the configured
Supabase project. No CLI, no MCP, no writes.

### The taxonomy migration is applied, and the data behind it is largely correct

| Check | Result |
|---|---|
| `/ureticiler` | **10 producer rows**, in `created_at desc` order — the reverse of `sourceProducers`, so the table, not the fixture |
| `/magaza/ege-ceviz` | **200.** "Kayadibi Köyü Aile Bahçesi", subtitle "Ceviz — Kayadibi Köyü Aile Bahçesi", one product: Kabuklu Ceviz ₺590,00 |
| `/magaza` source row | `kaynak=ciftlik`, `kaynak=secki`, `kaynak=mutfak` — all three present |
| `/shop/kabuklu-badem` | "Kabia Çiftliği" + **"Organik Sertifikalı"** |
| `/shop/tarhana` | "Kabia Mutfak" + "Kabia Seçki Standardı" |

`products.source`, `products.certification`, `products.producer_id` and `public.producers`
all exist and are populated. Producers are seeded and published, product sources are
individually correct, `producer_id` is assigned, and one product has been upgraded to
`organik_sertifikali` by hand — exactly the review the taxonomy migration's header said an
administrator would perform.

**Finding 1 is therefore void, and finding 4 with it.** The false-provenance window the
sequencing plan was built around had already been passed through safely. §5's steps 1, 2 and
4 describe a state that no longer held: `/magaza/ege-ceviz` works, `/ureticiler` lists ten
producers. What remains true from §5 is step 3 (the product form) and the *presentation*
half of step 4 — the page renders two editable strings and no per-producer hero, intro,
ordering or banner.

### Finding 5 was live, not latent, and much larger than source could show

The `categories` table holds nine categories — `bal`, `ceviz`, `eriste`, `findik`,
`ihlamur`, `kabuklu-badem`, `salca`, `sirke`, `tarhana` — and **none of them was in the
hardcoded five**. So `toCategory()` mapped *every product in the catalogue* to `cig-badem`,
and the store's category filter offered exactly one option for a nine-category catalogue.
Tarhana rendered as "Çiğ Badem • Kabia Mutfak". The category work had been done correctly in
admin and the storefront was discarding all of it.

| | Before | After |
|---|---|---|
| Category filter | `Tümü, Çiğ Badem` | `Tümü, Bal, Ceviz, Erişte, Fındık, Ihlamur, Kabuklu Badem, Salça, Sirke, Tarhana` |
| Kabuklu Badem | `Çiğ Badem • Kabia Çiftliği` | `Kabuklu Badem • Kabia Çiftliği` |
| Kabuklu Ceviz | `Çiğ Badem • Kabia Seçki` | `Ceviz • Kabia Seçki` |

### A finding the audit could not see: product creation was broken

`products.certification` is NOT NULL with **no database default** — the taxonomy migration
added it nullable, backfilled it, then set NOT NULL. The save action's insert payload never
mentioned it, so every product creation failed with SQLSTATE 23502, surfaced as the generic
"Zorunlu bir alan boş bırakılamaz." naming no field.

Traced against every NOT NULL column on `products`: it is the only one lacking both a
payload value and a database default. `products.source` is also NOT NULL and also absent from
the payload, but its `default 'ciftlik'` covered it — silently filing new products under the
farm. Fixed in `aecf57a`; `lib/admin/product-fields.ts` now holds the form/schema/payload/
select column contract as testable data.

### Also observed

Every one of the ten products read "Stokta yok" at the time of the check. Not investigated —
it may simply be true.

`a82a52a` ("sade rozet ve veritabanı destekli üretici mağazaları") did more than move
`/magaza/[producer-slug]` to the database: it deleted `SOURCE_BADGE_STYLE` and moved the
source out of the image badge into the metadata line as `{category} • {source}` on both the
product card and the detail page. That is why a wrong category now sits directly beside a
correct provenance claim, and why finding 5 mattered more than it first appeared.
